# AIOS · Инновации университета

Базовая (минимально жизнеспособная) версия платформы для практической сессии **«Агентный инжиниринг для управления инновациями в вузе»**. Аудитория — проректоры по инновациям и руководители подразделений. Платформа — прототип, который каждая команда докастомизирует под свой университет: добавляет свои данные, настраивает дашборд под свои метрики и создаёт своих ИИ-агентов через MD-файлы.

Что есть в каркасе:

- **Рабочий стол проректора** (`index.html`) — интерактивный дашборд: патенты и РИД, портфель проектов по УГТ 1–9 (проект на одном уровне 2 года и дольше подсвечивается красным как кандидат на закрытие), цепочка финансирования «РНФ → Гранты → Стартап-студия → Венчур», стартап-коллективы, трекер обязательств «Венчурного билдера».
- **Каталог и конструктор агентов** (`agents.html`) — шаблоны «Портфельный аналитик», «Аналитик экосистемы», «Венчурный билдер» и конструктор, который выгружает агента в `.md` со структурой: Назначение, Роль, Навыки (skills), Входные/Выходные данные, Ограничения.
- **Онбординг проекта вуза** — агент в рабочем чате за 7 шагов собирает карточку проекта университета и сохраняет её в «Проекты».

## Инструкция для участников сессии

### 0. Запуск платформы на своём компьютере

Нужен **Docker Desktop** (вариант А) или **Python 3.11+** (вариант Б).

**А. Docker (проще всего)**

```bash
git clone https://github.com/aponomareva010203-design/CSRNW-AIOS_spbgti.git
cd CSRNW-AIOS_spbgti
docker compose up --build
```

**Б. Python**

```bash
git clone https://github.com/aponomareva010203-design/CSRNW-AIOS_spbgti.git
cd CSRNW-AIOS_spbgti
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # Windows: copy .env.example .env
uvicorn api.main:app --reload --port 8000
```

Откройте **http://localhost:8000**. Остановить — `Ctrl+C` (Docker: `docker compose down`).

> Стартовый администратор создаётся при первом запуске: логин `admin@university.local`, пароль `admin12345` (меняются в `.env`: `AIOS_ADMIN_LOGIN`, `AIOS_ADMIN_PASSWORD` — до первого запуска). Чтобы агенты отвечали в чате, подключите LLM: «Админ-панель → Настройки внешних API» или переменные `AIOS_LLM_*` в `.env`. Дашборд, каталог и конструктор агентов работают и без LLM.

### 1. Регистрация и вход

1. На главной нажмите **«Войти»** → **«Создать аккаунт»**, введите e-mail и пароль, отметьте согласия.
2. Подтвердите e-mail по ссылке из письма. Локально почта не настроена — ссылка подтверждения печатается в окне терминала, где запущен сервер (строка `[DEV] SMTP не настроен — подтверждение e-mail … по ссылке: …`); откройте её в браузере.
3. Войдите. Для быстрого старта можно войти стартовым администратором (см. выше).

### 2. Онбординг: создать проект вуза

1. Откройте **«Кабинет»**, заполните «Данные пользователя» (ФИО, должность).
2. Нажмите **«Запустить онбординг проекта»** — откроется рабочий чат с агентом «Онбординг проекта».
3. Ответьте на 7 вопросов: вуз и название проекта, цель, ключевые метрики, команда, подразделения, бюджет и задел. Агент покажет сводку и сохранит карточку в раздел **«Проекты»**.

### 3. Дашборд: рабочий стол проректора

1. Откройте **«Рабочий стол проректора»** (главная страница, меню «Дашборды»).
2. Попробуйте интерактивность: фильтры перспективности РИД, клик по столбцу УГТ (фильтрует таблицу), флажок «Только кандидаты на закрытие», клик по стадии цепочки финансирования, по типу стартап-коллективов, фильтры статусов в трекере венчурного билдера. Подсказки появляются при наведении.
3. **Свои данные:** нажмите «Скачать шаблон данных», замените значения данными своего вуза и загрузите файл кнопкой «Загрузить свои данные» (хранится только в вашем браузере; «Вернуть демо-данные» — сброс). Чтобы данные увидели все пользователи — отредактируйте `data/dashboard.json`.

### 4. Выбрать шаблон агента

1. Откройте **«Агенты»** → блок **«Шаблоны агентов для проректора»**.
2. **«Скачать .md»** — получить готовый шаблон как есть; **«Открыть в конструкторе»** — загрузить его в форму для правки.

### 5. Собрать и выгрузить свой MD-файл

1. В **«Конструкторе агента»** выберите основу (шаблон или «Пустой шаблон») и отредактируйте поля: название, описание, Назначение, Роль, Навыки (skills), Входные данные, Выходные данные, Ограничения, сценарий работы, фразы-триггеры. Справа — итоговый файл.
2. **«Скачать .md»** — сохранить агента (имя файла формируется из названия).
3. **«Доработать в „Конструкторе агентов“»** — продолжить в диалоге с ИИ (нужен вход и подключённый LLM): агент сохранится черновиком в кабинете, после проверки его можно опубликовать.
4. Чтобы агент появился в каталоге вручную: положите файл в `data/skills/<id>.md` и добавьте карточку в `data/skills.json`:

```json
{
  "id": "my-agent",
  "category": "special",
  "name": "Мой агент",
  "domain": "Управление инновациями",
  "description_ru": "Что делает агент — одной фразой",
  "author": "Команда вуза",
  "recommended_model": "—",
  "file_url": "/data/skills/my-agent.md"
}
```

(`category`: `general` — шаблоны, `special` — агенты вашего университета, `service` — служебные.)

### Как настроить дашборд под свой вуз

Данные — `data/dashboard.json` (суммы в тыс. ₽):

| Блок | Поля |
|---|---|
| `university`, `stale_years`, `as_of` | название вуза; через сколько лет на одном УГТ проект становится кандидатом на закрытие (по умолчанию 2); дата расчёта (`null` — сегодня) |
| `patents[]` | `id`, `title`, `type`, `year`, `department`, `perspective` (`high`/`low`), `support_cost`, `licensee` |
| `projects[]` | `id`, `title`, `department`, `trl` (1–9), `trl_since` (дата перехода на текущий УГТ), `funding_stage` (ключ из `funding_stages`), `budget` |
| `funding_stages[]` | `key`, `title`, `subtitle` — стадии цепочки по порядку |
| `teams[]` | `name`, `funding` (`grant`/`internal`/`state`), `members`, `project` (id проекта) |
| `venture_tracker[]` | `startup`, `commitment`, `owner`, `due`, `progress` (0–100), `status` (`on_track`/`risk`/`overdue`/`done`; если не указан — рассчитывается по сроку и прогрессу) |

Логика виджетов — `frontend/js/dashboard.js`, вёрстка — `frontend/index.html`, цвета — токены в начале `frontend/css/style.css`.

## Архитектура

- **Фронтенд** — статический сайт на чистых HTML/CSS/JS в каталоге `frontend/`, без шага сборки (`npm run build` лишь сообщает, что собирать нечего).
- **Бэкенд** — FastAPI-сервис в `api/`: каталог моделей (`GET /api/models`), агентный рантайм-харнесс (`POST /api/chat`, `/api/sessions`, `/api/runtime`), серверная авторизация и админ-раздел (`/api/auth/*`, `/api/admin/*`), онтологии навыка-конструктора (`/api/ontologies*`), данные из `data/` (`/data/*`) и статика `frontend/` по корневому пути.
- **Агентный рантайм** — `api/runtime/`: цикл «LLM ↔ инструменты» с SSE-стримингом, OpenAI-совместимый провайдер (настраивается из админ-панели; mock остаётся только в тестах), инструменты знаний/каталога/файлов, файловое хранилище сессий, сборка системного промпта из навыков-агентов.
- **Автоматизации (n8n)** — self-hosted n8n работает движком раздела «Автоматизации» (`deploy/n8n/`, установка — `deploy/n8n/SETUP.md`): AIOS собирает воркфлоу из блоков пользователя и управляет ими через public API одного сервисного ключа (`api/runtime/n8n_*.py`, `api/routers/automations.py`). Пользователи n8n не создаются — права разграничивает AIOS; шаг «ИИ-агент AIOS» возвращается внутрь платформы (`POST /api/internal/agent-step` с секретом `X-AIOS-Service-Key`). Лицензия n8n Sustainable Use License допускает внутреннее использование — внешний доступ к n8n не предоставляется.
- **Единая точка доступа** фронтенда к данным — `frontend/js/api.js`, публикующий `window.AIOS_API`. Переход на выделенный бэкенд достигается изменением только `BASE_URL` внутри него.

### API

Эндпоинт `GET /api/models` возвращает `ModelsResponse` со списком карточек `ModelCard`:

| Параметр | Тип | Описание |
|---|---|---|
| `source` | `spbti` \| `huggingface` | Необязательный фильтр по источнику; неверное значение отклоняется схемой (HTTP 422) |

Поля `ModelCard` (`api/schemas.py`):

- `id`, `name` — идентификатор и название;
- `source` — `spbti` (сделано в университете) или `huggingface`;
- `provider`, `model_id` — поставщик и идентификатор на хабе;
- `image_url` — миниатюра;
- `description_ru` — описание (жёстко ограничено 200 символами на валидаторе);
- `tags` — список тегов;
- `access_url` — ссылка на модель;
- `is_placeholder` — флаг заглушки.

Текущий источник данных — встроенный seed-каталог (`api/catalog.py`). Планируется замена на Hugging Face Hub API без изменения контракта и интерфейса; токены Hugging Face на фронтенд не передаются.

## Запуск

### Docker

```bash
docker compose up --build     # или вручную:
docker build -t aios .
docker run -p 8000:8000 aios
```

Приложение поднимется на `http://localhost:8000` (порт можно переопределить переменной `PORT`).

### Локально (Python + uvicorn)

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # LLM можно задать позже в админ-панели; .env — запасной вариант
uvicorn api.main:app --reload
```

### Только статика

```bash
npm run dev   # npx serve . -l 5173
```

> Раздел «Репозиторий моделей» в этом режиме не заработает — он обращается к `/api/models`, поэтому нужен запущенный FastAPI (`api/main.py`).

## Развёртывание на VPS

Опробованная схема на этой машине (Ubuntu 24.04, доступ по IP без домена):

```
Интернет → https://<IP-сервера>.sslip.io (nginx :443, сертификат Let's Encrypt)
              ↳ HTTP :80 — редирект на HTTPS
              ↳ reverse_proxy → 127.0.0.1:8000 (systemd-сервис aios.service, uvicorn)
```

- **Приложение** — юнит `/etc/systemd/system/aios.service` (User=csrnw, WorkingDirectory=каталог проекта, `Restart=always`): `sudo systemctl restart aios` подхватывает изменения кода.
- **nginx** — сайт `/etc/nginx/sites-available/aios` (симлинк в sites-enabled): `proxy_buffering off` и таймауты 300с для SSE-стриминга `/api/chat`.
- **Секреты** — `.env` (LLM-эндпоинт опционален; `AIOS_ADMIN_LOGIN`/`AIOS_ADMIN_PASSWORD` — стартовый администратор, создаётся один раз при пустом хранилище `.aios-runtime/users`; `AIOS_SMTP_*` — SMTP-аккаунт для писем подтверждения e-mail; `AIOS_PUBLIC_BASE_URL` — публичный адрес сайта, из него строятся ссылки в письмах; `AIOS_USER_CONTEXT_INTERVAL` — период проходов планировщика контекстов кабинета, сек).
- **HTTPS без домена** — самоподписанный сертификат на IP (`/etc/nginx/ssl/aios-ip.{crt,key}`, 10 лет, SAN=IP). Браузер покажет предупреждение — принять исключение. Let's Encrypt по голому IP сертификаты не выдаёт.

Переход на домен, когда появится: A-запись домена → IP сервера, затем `sudo apt install certbot python3-certbot-nginx && sudo certbot --nginx -d <домен>` (заменит самоподписанный сертификат и настроит продление).

**Шпаргалка по эксплуатации**

| Действие | Команда |
|---|---|
| Статус/рестарт приложения | `systemctl status aios` / `sudo systemctl restart aios` |
| Логи приложения | `journalctl -u aios -f` |
| Логи nginx | `tail -f /var/log/nginx/aios.*.log` |
| Конфиг nginx | `sudo nginx -t && sudo systemctl reload nginx` |
| Обновление кода | правка файлов в каталоге проекта + `sudo systemctl restart aios` |
| Бэкап (пользователи, токены, сессии) | `tar czf aios-backup.tgz .aios-runtime data` |
| Восстановление бэкапа | распаковать в каталог проекта + `sudo systemctl restart aios` |

## Авторизация

Серверная авторизация (`api/routers/auth.py`): регистрация с подтверждением e-mail, вход, выход и профиль — эндпоинты `/api/auth/*`. Пароли хранятся только в виде PBKDF2-хеша с солью (`api/runtime/users.py`; JSON-файлы в `AIOS_RUNTIME_DIR/users` — вне git и вне публично раздающегося `/data`). Server-side Bearer-токены живут 7 дней (`api/runtime/tokens.py`, `AIOS_RUNTIME_DIR/auth`). На фронтенде сессия лежит в `localStorage` под ключом `aios-auth-v1` (те же имя и роль читают `pilot.js` и `workspace.js`), изменение сессии оповещается событием `aios-auth-change`; истёкший токен автоматически разлогинирует при следующей загрузке страницы.

Регистрация требует подтверждения адреса: на e-mail уходит письмо со ссылкой (`api/runtime/mailer.py`, SMTP Яндекса; настройки — `AIOS_SMTP_*` в `.env`). Токены подтверждения живут 48 часов и одноразовы (`api/runtime/confirmations.py`, `AIOS_RUNTIME_DIR/confirm`); повторная отправка переиспользует живой токен. Автовхода после регистрации нет; вход неподтверждённой учётки — 403 с предложением запросить письмо повторно. Пока `AIOS_SMTP_HOST` не задан, работает dev-фолбэк: письмо не отправляется, ссылка печатается в лог сервера. Форма регистрации запрашивает только e-mail и пароль (дважды, с проверкой совпадения); имя не собирается — в интерфейсе вместо имени показывается e-mail (API по-прежнему принимает опциональное `name`).

При первом старте (пустое хранилище) создаётся стартовый администратор — прежняя демо-учётка (логин — почта, пароль — `1234`); смените пароль после развёртывания. Seed-админ и учётки, созданные до введения подтверждения, считаются подтверждёнными. Новые регистрации получают роль «Пользователь».

### Админ-панель

Страница `admin.html` (пункт «Админ-панель» в нижней части левого меню, виден только роли «Администратор») показывает все регистрации: имя, логин, роль, дату регистрации и последний вход. Действия:

- смена роли «Пользователь» ⇄ «Администратор» (нельзя снять роль с последнего администратора);
- удаление пользователя с отзывом всех его токенов (собственную учётку удалить нельзя).

### Настройки внешних API (LLM)

Блок в админ-панели задаёт LLM для рабочего чата **всех пользователей**: endpoint (Base URL), API-ключ и модель. Приоритет настроек: админ-панель (файл `AIOS_RUNTIME_DIR/llm.json`) → `.env` → не настроено. Настройки применяются на лету, без рестарта. Кнопки:

- **«Загрузить модели»** — выпадающий список моделей, доступных ключу на эндпоинте (подойдёт любой OpenAI-совместимый API: OpenAI, proxyapi.ru, OpenRouter, vLLM, Ollama);
- **«Проверить соединение»** — минимальный тестовый запрос с показом задержки и ошибки API;
- **«Сохранить»** — ключ хранится только на сервере, в API отдаётся маской (`sk-…1234`).

### Об организации

Раздел админ-панели (`frontend/js/organization.js`, данные в `data/organization/`) из двух элементов:

1. **«Информация об организации»** — «Основная информация» (название, разворачиваемый список aliases, описание, направления деятельности) и «Показатели деятельности» (объем доходов от НИОКР; численность ППС, научных работников и студентов; средний балл ЕГЭ) с подписью источника данных. Правки записываются в исходные `profile.json` / `metrics.json`; дата последнего обновления (`updated_at`, `ДД.ММ.ГГГГ`) проставляется сервером автоматически. Сейчас заводится универсальный шаблон университета (`type: "university"`): поля описаны в самих JSON (`id`, `title`, `type`), поэтому будущие типы организаций со своими наборами полей не потребуют правок кода.
2. **«Основные документы»** — три категории: Стратегия, Программа развития, Другие документы. Файлы загружаются через интерфейс в `data/organization/objects/` (реестр — `documents.json`), показываются карточками с иконкой расширения и скачиваются по клику. У каждого документа — короткое **.md-описание** основного содержания: его первым читает ассистент, полная PDF-версия — только по необходимости.

Доступ ассистента к разделу — инструментами `get_organization` и `read_document` (см. «Агентный рантайм»): JSON-данные и .md-описания читаются без ограничений, большие PDF — только после явного разрешения пользователя в диалоге.

### Кабинет

Страница `cabinet.html` (раздел «Рабочее пространство» левого меню, виден после входа) — блок **«Данные пользователя»**: ФИО, должности (динамические строки, до 10), учёная степень и научные интересы. Хранятся в `AIOS_RUNTIME_DIR/user/{id}-profile.json`; редактировать можно только собственный блок — идентификатор берётся из Bearer-токена (`api/routers/cabinet.py`, `api/runtime/cabinet.py`).

**Онбординг нового пользователя:** если блок «Данные пользователя» не заполнен, `POST /api/auth/login` отвечает `profile_filled: false`, и после входа фронтенд ведёт на `cabinet.html?onboarding=1`. После сохранения анкеты платформа сама открывает рабочий чат с активным навыком «Онбординг проекта» и отправляет стартовое сообщение (флаг навыка с `prompt` в `localStorage` ставит `cabinet.js`, автозапуск выполняет `workspace.js`).

Второй блок, **«Контекст о пользователе»** (`user/{id}-context.json`), в интерфейсе не отображается и через API не отдаётся: его составляет языковая модель не чаще раза в сутки на пользователя (`api/runtime/user_context.py`, фоновая задача запускается в `lifespan`) по двум источникам, видимым платформе, — собственным сессиям с нейросетью (привязка к учётной записи по токену в `POST /api/chat`) и упоминаниям пользователя в сессиях других (ФИО/фамилия с инициалами, логин). Перегенерация — только при новом материале (sha256-дайджест собранного материала), иначе обновляется лишь отметка проверки; блок ограничен 1000 символами и попадает в системный промпт ассистента вместе с анкетой (анкета передаётся с запретом на дублирование). Оба блока удаляются вместе с учётной записью. Периодичность проходов планировщика — `AIOS_USER_CONTEXT_INTERVAL` (сек, по умолчанию 3600; без настроенной LLM проходы пропускаются).

## Рабочий чат

Чат-панель (`frontend/js/workspace.js`) доступна после входа с любой страницы: пункт «Рабочий чат» в разделе «Рабочее пространство» левого меню (весь раздел виден только вошедшим) и золотая плашка на главной. Панель наползает справа поверх страницы, растягивается за левую кромку (или кнопкой ⛶) до полного экрана. Разметку панели скрипт инъецирует в DOM, поэтому страницам достаточно подключить `js/api.js` и `js/workspace.js`.

Секция «Контекст» (чипы агентов/навыков и автоподгрузка знаний, каталога и файлов) убрана: ничего не подгружается в рабочий чат автоматически. Подбор навыков и систем знаний появится позже — рекомендациями в самом чате (см. дорожную карту).

- **Модель** — задаётся администратором централизованно (админ-панель → «Настройки внешних API»); текущий статус виден в шапке панели (`GET /api/runtime`). Без настроенной LLM чат отвечает 503 с понятным сообщением.
- **Диалог** — потоковые ответы через агентный рантайм (`POST /api/chat`, SSE): текст печатается по мере генерации, вызовы инструментов показываются карточками, ошибки — событием в чате. Кнопка «＋» начинает новый диалог, транскрипт прошлой сессии восстанавливается при повторном открытии панели.

Администратор на странице пилота может:

- менять статус любого артефакта: клик по чипу открывает пояснение с кнопками статуса (`PATCH /api/pilot/projects/{id}`, сохраняется на сервере).

Страница «Статус пилотного проекта» строится на сервере из активных карточек
пользователей («Мои проекты», статус `active`): тематика — название карточки,
ФИО руководителя — анкета «Кабинета» владельца (иначе имя учётной записи).
Статусы артефакта: «не начато» (0), «гипотеза сформулирована» (1), «в процессе
создания» (2), «завершено» (3); гипотезы по каждому артефакту хранятся в
карточке (блок `artifacts`, пишут навык «Онбординг проекта» инструментом
`save_project_card` и владелец через `PATCH /api/projects/{id}`). Клик по чипу
со статусом «гипотеза сформулирована» и далее открывает пояснение с гипотезой
проекта по этому артефакту. Данные больше не хранятся в `localStorage` —
таблица едина для всех посетителей и читается с `GET /api/pilot/projects`
(публичный эндпоинт, персональные поля карточки наружу не отдаются).

## Telegram-бот

Тот же чат с агентами и базами знаний, что и на сайте, — в Telegram (`api/routers/telegram.py`). Бот работает от имени учётной записи платформы: личные настройки LLM («Настройки»), учёт расхода токенов и лимиты, кабинетный контекст в промпте и доступ к RAG-базам — всё как в веб-чате, потому что ход выполняется тем же кодом (`run_agent_loop`): инструменты, `search_corpus` по подключённой базе, кабинетный контекст, журнал решений. Ответ приходит финальным сообщением (SSE в Telegram не нужен); пока агент работает с инструментами, бот держит «печатает…». Длинные ответы режутся на куски ≤4096 символов, маркдаун конвертируется в подмножество HTML Telegram с откатом на чистый текст.

**Привязка** — без ввода пароля боту: `/start` в боте выдаёт одноразовый код (15 минут) с кнопкой-ссылкой `settings.html#tg-link=КОД`; пользователь подтверждает привязку в «Настройках» → Telegram (deep-link подставляет код сам, либо код вводится вручную). Эндпоинты: `GET/POST/DELETE /api/auth/telegram/link`. Один Telegram — одна учётная запись; отвязка — `/unlink` в боте или кнопка в «Настройках». Привязки, коды и состояния чатов — `AIOS_RUNTIME_DIR/telegram/` (вне git и вне публичного `/data`); сессии бота — обычные сессии чата, видны в «Истории сессий».

**Меню-клавиатура** (постоянные кнопки внизу чата, ставится `/start` и `/help`): `🤖 Вызвать агента` — выбор агента каталога кнопками (агент стартует в новом диалоге, как в вебе), `📚 База знаний` — подключить RAG-базу из опубликованных (или «без базы»), `✨ Новый диалог`, `ℹ️ Статус`. Команды в кнопке «Меню»: `/new` (агент и база сохраняются), `/status`, `/help`, `/unlink`; `/agents` и `/base` продолжают работать для совместимости. Групповые чаты — следующий шаг (MVP — только личные).

**Подключение**:

1. `@BotFather` → `/newbot` → токен в `.env`: `AIOS_TG_BOT_TOKEN`;
2. секрет вебхука `AIOS_TG_WEBHOOK_SECRET` (произвольная случайная строка);
3. зарегистрировать вебхук: на сервере уже настроено всё для `https://<адрес>/api/telegram/webhook` (nginx проксирует `/api`, сертификат Let's Encrypt Telegram принимает) — админ нажатием: `POST /api/telegram/webhook/setup` (использует `AIOS_PUBLIC_BASE_URL`), либо вручную `curl "https://api.telegram.org/bot$TOKEN/setWebhook?url=https://<адрес>/api/telegram/webhook&secret_token=$SECRET"`;
4. локальная разработка без публичного HTTPS — `AIOS_TG_POLLING=1` (long polling вместо вебхука; при установленном вебхуке Telegram отвечает 409 и polling останавливается).

**Cloud.ru: работает long polling, вебхук недоставляем.** Хостинг режет трафик с Telegram в ОБЕ стороны: наружу спасает закреплённый IP в `/etc/hosts` (см. ниже), но входящие POST от Telegram к вебхуку теряются (`getWebhookInfo`: `last_error_message: "Connection timed out"`, апдейты копятся в `pending_update_count`). Режим `AIOS_TG_POLLING=1` (в `.env` на сервере) снимает проблему: все соединения инициирует наш сервер — установленный вебхук перед включением удаляется (`deleteWebhook`), иначе getUpdates отвечает 409. Живость поллера: `sudo ss -tnp | grep 149.154.167.220` — ESTAB-соединение uvicorn (long poll держит канал ~25 с). Для другого хостинга без блокировок предпочтительнее вебхук.

**Блокировка Telegram на хостинге (актуально для Cloud.ru)**: исходящие соединения к части диапазонов Telegram режутся (TCP до `149.154.166.110:443` теряется молча, github/openai при этом доступны). Обход без прокси: у `api.telegram.org` несколько дата-центров, и `149.154.167.220` доступен — в `/etc/hosts` добавлена строка `149.154.167.220 api.telegram.org` (IPv6 из DNS падает мгновенно «нет маршрута», клиент откатывается на IPv4). Если бот однажды замолчит (`GET /api/telegram/status` отвечает 502 «ConnectTimeout») — проверить доступность: `curl -m 5 https://api.telegram.org/`; если этот DC тоже закрыли, сменить IP в `/etc/hosts` на живой (`getent ahostsv4 api.telegram.org` с другой машины или любой из 149.154.167.0/24) либо настроить `AIOS_TG_PROXY`.

**DPI «плавает»**: TCP до живого DC открывается, но TLS с SNI api.telegram.org периодически буксует (ConnectTimeout). Клиент бота повторяет неоткрывшееся соединение с паузами 1/3 с (запрос при неоткрывшемся канале гарантированно не ушёл — дубли исключены), поллер циклится бесконечно — сообщения доходят, иногда с задержкой в десятки секунд. Богатые ответы агента передаются в Telegram полностью: ```aios-choices превращаются в inline-кнопки (клик отправляет вариант как сообщение пользователя), графики chart_generate растеризуются (`api/runtime/chart_png.py`, Pillow + системный DejaVu) и приходят фото после текста; длинные ответы режутся на куски до конвертации в HTML (`telegram_chunks`), поэтому теги не рвутся на границе и ответ не откатывается в плоский текст со «звёздочками».

Диагностика: `GET /api/telegram/status` (админ) — `getMe`, `getWebhookInfo`, число привязок. Сетевых зависимостей в коде бота нет: Bot API вызывается минимальным httpx-клиентом (`api/runtime/tg_client.py`, без SDK — как и провайдер LLM).

## Агентный рантайм (харнесс)

Панель «Рабочий чат» — клиент агентного рантайма `api/runtime/`:

```
сообщение → POST /api/chat → системный промпт (файлы api/runtime/prompts/*.md:
           базовая роль + агент + навыки) → цикл «LLM ↔ инструменты»
           (до AIOS_MAX_TOOL_ITERATIONS шагов)
           → SSE-события: session / delta / tool_call / approval_request /
             approval_result / tool_result / done / error
```

| Эндпоинт | Назначение |
|---|---|
| `POST /api/chat` | Сообщение ассистенту; ответ — поток SSE. Тело: `{message, session_id?, agent_id?, skill_ids?}`. Модель задаёт администратор; без настроенной LLM — 503 |
| `POST /api/chat/approvals` | Решение человека по карточке подтверждения действия агента: `{session_id, approval_id, decision: approve\|decline}`; повторно решённый запрос — 409 |
| `GET /api/chat/skills-suggest?q=` | Подсказки навыков по фразам-триггерам из frontmatter (публичный, для чипов над полем ввода) |
| `GET /api/stage-map` | Карта этапов конвейера (`data/stage-map.json`, правится без перезапуска) |
| `GET /api/sessions` | Список сессий (сводки) |
| `GET /api/sessions/{id}` | Полный транскрипт сессии и журнал решений (`decision_log`) |
| `DELETE /api/sessions/{id}` | Удалить сессию |
| `GET /api/runtime` | Статус: настройка LLM (`live`/`not_configured`) и модель, инструменты |
| `GET /api/projects` | Карточки проектов владельца токена («Проекты»), свежие сверху |

- `search_knowledge` — подбор RAG-баз (`data/rag_bases.json`) и онтологий (`data/ontologies.json`) по запросу; полнотекстовый поиск по корпусам подключается отдельным инструментом;
- `get_catalog` — каталог моделей/агентов/навыков;
- `get_organization` — данные раздела «Об организации» (profile/metrics/documents с .md-описаниями); JSON читаются без ограничений;
- `read_document` — документ организации: без `full` возвращает короткое .md-описание; с `full=true` — полную версию (текстовые файлы сразу; PDF >100 КБ — диалоговое разрешение: инструмент отвечает `needs_permission`, модель спрашивает пользователя, после его ответа повторный вызов с `confirmed=true` читает текст через `pypdf` с лимитом символов и диапазоном страниц);
- `get_projects` — карточки проектов текущего пользователя со страницы «Проекты»; работает только для авторизованных (привязка сессии к учётной записи по Bearer-токену);
- `save_project_card` — создаёт или обновляет карточку проекта (upsert по `project_id`); первое сохранение всегда `draft`, статус `active` — только после явного подтверждения пользователя;
- `read_file`, `list_files`, `write_file` — файлы `data/` в песочнице `AIOS_TOOLS_ROOT`.

**Химические инструменты** (`api/runtime/chemistry_tools.py` — порт инструментария ChemCrow без зависимости от пакета): RDKit-вычисления исполняются в расчётной песочнице (rdkit уже в `/opt/aios-sandbox/venv`), сетевые — httpx-ом. Регистрируются только те, чья инфраструктура доступна:

- `chem_mol_convert`, `chem_descriptors`, `chem_functional_groups`, `chem_similarity`, `chem_substructure`, `chem_reaction_check` — представления молекулы, дескрипторы и Липински, функциональные группы по SMARTS, сходство Танимото, подструктурный поиск, проверка reaction SMILES с атомным балансом (нужна песочница);
- `chem_depict` — 2D-рисунок структуры/реакции (PNG-вложение чата, как артефакты `run_calc`);
- `chem_control_chem_screen` — информационный скрининг SMILES/CAS по списку контролируемых веществ ОЗХМ (`api/runtime/chemistry_data/control_chem.csv` — в пакете, не в перезаписываемой `data/`); не официальная экспертиза;
- `chem_safety_lookup` — GHS-классификация из PubChem (сигнальное слово, пиктограммы, H-/P-коды, взрывоопасность);
- `rxn_retrosynthesis`, `rxn_forward` — ретросинтез и предсказание продуктов через IBM RXN; регистрируются только при `AIOS_RXN_API_KEY` в `.env` (базовый URL инстанса с совместимым REST-API — `AIOS_RXN_BASE_URL`); обработчик сам поллит асинхронную задачу (бюджет 90/150 с) и переиспользует проект `AIOS Chemistry Tools`.
  - Облачный IBM RXN со временем перестанет поддерживаться; официальный self-hosted преемник [rxn-sandbox](https://github.com/rxn4chemistry/rxn-sandbox) отдаёт предсказания через Jupyter/Python и MCP-сервер, а не через совместимый REST — для него нужна отдельная интеграция (например, MCP-клиент платформы).

**Провайдеры** (`api/runtime/providers.py`): любой OpenAI-совместимый эндпоинт (OpenAI, proxyapi.ru, OpenRouter, vLLM, Ollama); конфигурация — из админ-панели (приоритет) или `.env`. Без настроенной LLM `/api/chat` отвечает 503; MockProvider остаётся только в тестах.

**Сессии** (`api/runtime/sessions.py`) — JSON-файлы в `AIOS_RUNTIME_DIR/sessions` (по умолчанию `.aios-runtime/`, вне git). Транскрипт, включая вызовы инструментов, сохраняется после каждого шага. Заголовок после первого обмена генерируется моделью по смыслу (`api/runtime/session_title.py`, один дешёвый запрос без инструментов; ошибка молча оставляет прежний заголовок).

**Практики human-in-the-loop из Dr.Claw** (перенесены концепции, без чужого кода):

- *Подтверждение действий* (`api/runtime/approvals.py`) — **по умолчанию выключено** (решение от 23.09.2026: без подтверждений работало лучше). При включении перечислением инструментов в `AIOS_APPROVAL_TOOLS` (например `write_file, notify, make_document, save_project_card, attach_project_file, save_ontology, save_rag, save_agent`) они исполняются только после кнопки «Утвердить» в чате; ожидание ограничено `AIOS_APPROVAL_TIMEOUT` (55 с), тишина считается отказом; правила для модели подмешиваются в промпт только при включённом gate.
- *Журнал решений* (`decision_log` сессии, append-only): установка этапа, генерация заголовка и (при включённом gate) подтверждения — аудит виден в `GET /api/sessions/{id}`.
- *Подсказки навыков*: каждый `data/skills/*.md` носит YAML-frontmatter (`triggers` — фразы-триггеры, `stage` — этап конвейера, `version`, `status`, опционально `references` — справочники, подгружаемые моделью через `read_file` по мере необходимости вместо вшивания в промпт). Пока пользователь печатает, панель показывает чипы подходящих навыков (`GET /api/chat/skills-suggest`, запуск — в новую сессию существующим механизмом).
- *Этапы конвейера*: `data/stage-map.json` (онтология → RAG → агенты → модели → полигон → соцсеть; hot-reload по mtime). Сессия навыка получает `stage` (в SSE-событии и API); чип «следующий этап» в чате отключён (некорректная работа, код за флагом `STAGE_NEXT_ENABLED` в workspace.js).

**Карточки проектов** (`api/runtime/projects.py`) — JSON-файлы в `AIOS_RUNTIME_DIR/projects/{user_id}/`: приватное хранилище (доступ только по Bearer-токену, не в публичной `data/`). Карточку собирает навык «Онбординг проекта» инструментом `save_project_card` (upsert по `project_id`, статусы `draft`/`active`); страница «Проекты» (растянута на всю ширину) читает их через `GET /api/projects*`, правит кнопкой «Редактировать» (`PATCH`, руководитель проекта — владелец) и удаляет кнопкой «Удалить» (`DELETE`, только администратор). Динамические блоки системного промпта («Об организации», «Проекты») подмешиваются по упоминаниям в вопросе (`api/runtime/skill_context.py`).

**Обратная связь каталога агентов** (`api/runtime/agent_feedback.py`) — звёзды, публичные комментарии и автоматическая статистика применения агентов в проектах; JSON-файл на агента в `AIOS_RUNTIME_DIR/agent_feedback/`. Применение пишется автоматически: инструменты `save_project_card / save_ontology / save_rag / save_agent` отмечают активных агентов сессии (`skill_ids`) в проекте артефакта (`project_id`), повторные запуски наращивают счётчик. Наружу (`/api/catalog/agents*`) отдаются названия проектов и имена авторов из анкеты — логины (e-mail) и персональные поля карточек не раскрываются. **Удаление агента** — кнопка в модалке каталога (видна только роли «Администратор»; роль проверяет сервер через `/api/auth/me`): `DELETE /api/catalog/agents/{id}` убирает карточку из `data/skills.json`, .md-файл агента и, если есть runtime-экземпляр `agt-{id}`, его целиком (записи, evals, трассы, публикация).

**Страница агента `/agent.html`** — карточки пользовательских агентов (`agt-…`, `agent_store.py`). Интерфейс собирается декларативно: платформа вычисляет блоки по составу инструментов (`compute_views`/`compute_console`), а конструктор агента при сборке передаёт в `save_agent` необязательное поле `ui` — тема (`theme: default|forest|graphite|light`), плотность (`density: comfortable|compact`), акцент (`accent: green|gold|blue|red|teal|graphite`) и вводный текст (`intro`) — один-два предложения, что агент делает и что человек получает на выходе. Никакого HTML/JS из карточки: значения из белых списков (`_normalize_ui`), страница применяет их CSS-классами; агенты без `ui` (старые) выглядят как раньше. Панель **«Расписание и уведомления»** (кнопка владельца) закрывает то, что раньше было настроить неоткуда: триггер по расписанию (интервал, дни недели, «не раньше» часа — `PATCH /api/agents/{id}` с `trigger`), кнопка «Запустить сейчас» (`POST /api/agents/{id}/run`) и личный SMTP-канал для писем агентов (`/api/settings/agent-mail*`, `user_mail.py`): личные настройки перекрывают общий SMTP платформы только для писем этого пользователя; проверка — реальное письмо на собственный адрес. Без расхождения: фоновый запуск требует published-агента с автономностью «работает сам» и выше (`agent_scheduler.py`), интервал не чаще раза в 15 минут, `weekdays`/`time` только сужают ритм. **Удаление агента** — кнопка «Удалить агента» (видна только роли «Администратор», как и `DELETE /api/agents/{id}`): полное удаление карточки, накопленных данных (записи, прогоны тестов, трассы исполнений) и публикации в каталоге; владелец и участники получают 403.

Модули рантайма и авторизации покрыты смоук-тестами: `pytest` (см. `tests/test_runtime.py`, `tests/test_auth.py`).

### Логотипы артефактов

Каждая онтология, RAG-база и агент получает **уникальный SVG-логотип по содержанию карточки** (название, описание, домен, теги): LLM рисует минималистичную пиктограмму в фирменной палитре, ответ проходит строгий allowlist (`sanitize_svg` из `project_icons.py`), файл сохраняется в `data/icons/{artifact_id}.svg` и публично отдаётся как `/data/icons/{artifact_id}.svg`. Механика — `api/runtime/artifact_icons.py`:

- генерация запускается **фоном сразу после сохранения** артефакта инструментами-конструкторами (`save_ontology` / `save_rag` / `save_agent`), не задерживая ответ в чате; повторные сохранения не перегенерируют логотип;
- `catalog_entry()` хранилищ подставляет `image_url` из файла логотипа (нет файла — прежний плейсхолдер), фоновая генерация точечно пропатчивает `image_url` в уже опубликованной карточке;
- у агентов логотип дополнительно пишется в поле `icon` приватной карточки (`AgentStore.set_icon`, без bump версии) и виден на странице `/agent.html`;
- кабинет и страница «Агенты» пробуют `/data/icons/{id}.svg` с откатом на заглушку по `onerror` — черновики без `image_url` тоже получают логотип;
- разовый бэкфилл существующих артефактов (включая навыки из `skills.json`) — `./.venv/bin/python3 scripts/generate_artifact_icons.py`, идемпотентен.
